# AI Note Taking Skill

## Shared Obsidian Conventions

Before creating or updating a note, read and follow the shared rules in the shared Obsidian note-taking reference: use `../../_shared/obsidian-note-taking-reference.md` in this repository, or the adjacent `obsidian-note-taking-reference.md` after installation. This reference is the authoritative common layer for all note-taking skills; the AI-specific rules below add domain behavior and take precedence only when they are more specific. If duplicated generic guidance conflicts with the shared reference, follow the shared reference.

## Mission

把用户提供的 AI 学习资料、已经解决的问题、实验记录或讨论内容，整理成以后可以复习、搜索和复用的个人知识笔记。

目标不是写一篇泛泛的 AI 教材，而是保留：

- 用户真正要学习或解决的问题；
- 核心概念、关键区别和适用条件；
- 可复现的代码、命令、配置、公式和参数；
- 实验环境、数据、指标、结果与限制；
- 论文或官方资料中的可验证结论；
- 真实截图、图表、错误信息和操作路径；
- 与已有笔记之间有意义的关系。

笔记应当像用户已有笔记的自然延续：以中文为主，保留英文 AI 术语、模型名、库名、API 名、代码标识符和必要的原文关键词；每篇笔记首次出现的重要英文专业术语后紧跟标准日语专业词汇，例如 `attention（注意機構）`。保留英文原文片段时，也为关键专业词加上日语对照。

## 1. Trigger Condition

只有用户明确要求记录、整理、生成笔记或把资料写进 Obsidian 时使用本 skill。例如：

- `整理这份 AI 学习资料`
- `帮我记一下这个 LLM 知识点`
- `把刚才的内容写成笔记`
- `整理这篇论文`
- `记录这个实验结果`
- `生成 AI 笔记`

AI 问答本身不等于需要写入笔记；没有记录意图时，只回答问题。

## 2. Primary Objective

笔记应能回答：

> 几个月后再次遇到这个主题时，我能否快速知道它是什么、为什么重要、如何使用、有哪些前提、我实际观察到了什么，以及容易在哪里出错？

优先级：

1. 可复用性和可搜索性；
2. 技术准确性与证据边界；
3. 代码、公式、实验和操作的可执行性；
4. 与已有知识的连接；
5. 简洁和符合用户习惯。

不要为了“完整”加入与原资料无关的历史、背景或低概率边界情况。

## 3. Read and Classify Before Writing

先完整阅读用户提供的资料和上下文，再提炼真正值得保留的知识。动态判断领域，不要局限于固定分类。可能包括：

- AI 基础、线性代数、概率统计、信息论；
- Machine Learning、Deep Learning、Computer Vision、NLP；
- LLM、Transformer、Tokenization、Embedding、推理；
- Prompt Engineering、RAG、Agent、Tool Use、Memory；
- Fine-tuning、LoRA/PEFT、RLHF、DPO、蒸馏、量化；
- Reinforcement Learning、Generative AI、多模态；
- 数据处理、训练、评估、可观测性、MLOps、部署；
- AI Safety、Responsible AI、隐私、版权、偏差；
- 论文阅读、开源项目、API/SDK、具体模型或框架。

记录已知的领域、主题、子主题、模型/算法、数据集、框架、版本、硬件、任务类型和来源。若无法确定，不要猜测，使用 `[待确认]`。

同时判断笔记类型：

- **概念笔记**：定义、直觉、机制、公式、与相近概念的区别；
- **教程/操作笔记**：环境、输入、步骤、输出、验证和注意点；
- **论文笔记**：问题、方法、贡献、证据、假设、局限和启发；
- **实验笔记**：目标、设置、变量、基线、指标、结果、解释和后续实验；
- **问题排查笔记**：现象、复现条件、证据、根因、修复和验证；
- **错题/误解笔记**：把题目还原成可迁移的知识，而不是保存题目本身；
- **项目实践笔记**：目标、架构、决策、实现、取舍、风险和待办。

一个主题可以是混合类型，但应选择一个主要组织方式，避免把同一内容拆成许多重复笔记。

## 4. Source Boundary and Accuracy

用户提供的资料是主要来源。区分三类内容：

- **资料明确说明**：保留来源中的结论，并在必要处记录页码、章节、图表或链接；
- **用户实际观察**：例如训练日志、报错、指标和系统行为，明确写成“本次实验中观察到”；
- **整理者推断**：只能写成“可能”“推测”“需要验证”，不能升级为已确认事实。

不要伪造论文结论、实验数字、模型能力、版本行为或引用。资料缺失时使用 `[待确认]` 或 `[需要实际实验确认]`。如需要外部资料进行核验，优先使用论文原文、官方文档、官方仓库或模型卡，并在笔记中将外部结论与个人观察分开。

### 4.1 AI 工具名称与内容适配

当来源材料出现 `Claude` 或直接面向 Claude 的提示词、操作说明和示例时，按照用户要求将其统一改写为与 Codex 对应的内容：保留原任务目标和语义，把工具名称、称呼和提示词中的对象替换为 `Codex`。如果原内容依赖某个特定平台或模型的专属功能，不要臆测 Codex 具有完全相同的能力；应改写为 Codex 可以合理完成的通用表达，或标记 `[待确认]` / `[需要实际实验确认]`。除非用户明确要求记录历史对照，最终生成的笔记中不应残留旧工具名称。

## 5. Preserve Personal Note Style and Metadata

先观察同目录或相关笔记的语言、标题层级、YAML、编号、目录、标签和文件命名方式，再遵循已有风格。默认中文表达，但不要强行翻译这些内容：

- Transformer、Attention、RAG、Agent、Embedding、Fine-tuning 等英文术语应保留原词，并在首次出现时附标准日语专业词汇，例如 `Embedding（埋め込み表現）`；
- 模型名、数据集名、框架/API/CLI 名称；
- 代码、配置键、参数名、文件路径和错误消息；
- 论文标题、作者、版本号和官方 UI 文案。

如果创建或更新 Obsidian YAML 标签，标签值中的空格改成短横线，例如：

```yaml
tags:
  - Large-Language-Model
  - Retrieval-Augmented-Generation
```

不要为了统一而重写用户原有内容；只在新增内容处保持一致。

## 6. Structure and Directory

根据笔记类型选择结构，不要把所有主题强行套进 `# AI` → `## ...` 的层级。

概念笔记通常使用：

```markdown
# 主题

**领域：** LLM / Transformer
**核心问题：** ...

## 是什么
## 为什么需要
## 如何工作
## 与相近概念的区别
## 注意点
```

论文笔记通常使用：

```markdown
# 论文标题

## 要解决的问题
## 核心方法
## 关键实验与结论
## 局限与我的理解
```

如果笔记中的实际一级和二级标题总数超过 2 个，在 YAML 后立即添加 `## 目录`；否则可以省略。目录必须覆盖笔记中的所有相关一级、二级标题，并遵循现有笔记的编号和 Obsidian 锚点风格。修改章节时同步检查编号、目录、锚点和引用，避免重复或失效链接。

“注意点”“易错点”“Tip”如果能归属于某个主题，应放到该主题后面，不要单独堆积一个无归属的章节。使用 Obsidian callout 表示提醒：

```markdown
> [!TIP] 易错点
> RAG 的检索质量和生成模型本身是两个需要分别评估的部分。
```

## 7. Content Rules by Note Type

### 7.1 概念、算法和公式

说明“是什么、解决什么问题、核心机制、输入输出、适用条件、局限”。公式使用 LaTeX，并定义符号、张量形状、单位或取值范围；不要只复制公式而不解释它在直觉上做了什么。对容易混淆的概念使用对比表或短例子，例如：

| 概念 | 解决的问题 | 关键区别 |
| --- | --- | --- |
| Fine-tuning | 改变模型参数以适应任务 | 训练成本和参数更新范围更高 |
| RAG | 在推理时注入外部知识 | 不直接改变基础模型参数 |

只有确实有助于理解时才加入表格或图示。

### 7.2 操作、代码和配置

按实际路径记录：

```text
环境/入口 → 输入 → 执行步骤 → 输出 → 验证结果 → 常见问题
```

重要代码必须放入带语言标记的代码块；保留有助于理解的注释，不要把关键配置埋在普通段落里。

```python
response = client.responses.create(
    model="<model-name>",
    input="...",
)
# ↑ model 需要替换成实际可用的模型名称
```

保留真实的命令、环境变量名、依赖版本、关键超参数和输出；涉及密钥、个人数据或内部地址时进行脱敏，不把秘密写进笔记。

### 7.3 实验与评估

尽量记录：

- 目标与假设；
- 环境：模型/框架/版本/GPU/数据集；
- 输入、预处理、训练或推理配置；
- baseline、对照变量、随机种子（如果有）；
- 指标定义与实际结果；
- 失败实验和异常现象；
- 结果解释、局限和下一步。

不要只记录“效果变好了”；保存足以判断结果可信度的数字和对比条件。无法确认因果关系时，写成相关性或观察结果。

### 7.4 论文和外部资料

围绕可复用的理解整理：研究问题、核心 idea、方法流程、主要贡献、实验支持、前提假设、局限、与已有概念的关系。不要把摘要逐句翻译成笔记，也不要把论文作者的主张写成已被普遍证明的事实。保留 DOI、arXiv、官方项目页或直接文档链接。只有存在实际可用的外部参考链接时，才在笔记中添加 `## 外部参考`；如果没有可保留的外部链接，就省略这个标题，不要留下空标题。

### 7.5 错题与误解

先提炼考查的概念、判断规则、相近选项的区别和错误原因，再写入最相关的知识章节。不要直接复制题干、完整选项、答案编号、判题反馈或测验截图。笔记脱离原题后仍应能帮助解决同类问题。

## 8. Images, Charts, and Evidence

如果实际图片、截图、训练曲线、架构图或错误截图可访问，且图片本身比文字、公式或表格更能表达结构、趋势、空间关系、界面位置或证据：

1. 复制到该主题约定的 `Assets` 文件夹；
2. 使用稳定、可读、避免覆盖的文件名；
3. 在笔记中用 Obsidian embed 直接插入；
4. 只有在图片不可访问时才使用 `[图片：...]` 占位符。

图片嵌入后，必须在图片前后补充可检索的文字解读：说明图中的关键对象、箭头/坐标/颜色/层级/界面区域的含义，以及它如何支持该知识点、实验结论或操作判断。不能只贴图而让读者自行猜测。若文字、公式或表格已经能够清楚准确地表达内容，则不必截图；若截图只是错题分析证据而不是可复用的学习材料，默认不嵌入。不要伪造图片，不要把临时路径、剪贴板路径或不稳定外链写进笔记。

### 8.1 集中 Assets 时的稳定引用与失效排查

当本地 Obsidian 笔记库把 AI 图片统一集中到一个 Assets 文件夹时，优先使用 Assets 中唯一的文件名进行嵌入：

```markdown
![[training-loss.png]]
```

本地笔记库已确认：带完整文件夹路径的嵌入写法在部分情况下会被 Obsidian 显示为“找不到文件”。因此，除非现有笔记库明确要求路径写法，不要在新建或批量整理的 AI 笔记中使用完整路径引用；如果存在同名文件，再根据现有库的稳定目录约定选择明确的相对路径。

完成笔记整理或迁移后，必须批量扫描所有图片嵌入：确认引用的文件名在目标 Assets 文件夹中存在，确认没有临时目录、剪贴板路径或旧 Assets 路径，并修正失效引用；该检查不能只针对用户截图中显示的单张图片。

## 9. Existing Notes, Linking, and Location

写入前搜索相关文件名、标题、关键词、模型名、算法名、框架、论文标题和错误消息。

按以下顺序处理：

1. 已有合适的一级或二级标题：只补充新信息，避免重复；
2. 属于已有笔记但没有合适标题：在该笔记内新增简洁章节；
3. 多篇相关笔记：选择一篇作为主要归档位置；只有读者需要跳转才能理解当前内容时，才在正文相关位置加入最少的内部链接；
4. 没有相关笔记：根据索引、Canvas、文件夹名和相邻笔记确定目录，再创建新笔记。

如果即将记录的内容与已有笔记中的内容重复或等价，直接在原有笔记、条目或对应标题下面补充本次新增的信息；完全相同的内容无需再次记录，也不要另建重复条目或笔记。

内部链接从简：只有当读者在当前段落确实需要打开另一篇笔记，才能更好理解、验证或完成当前知识点时，才添加 `[[Wiki Link]]`，并直接放在解释该关系的正文位置。只因主题相近、同属 AI 或出现在同一课程中，不足以加链；目标文件名不确定时不猜测。

不要在笔记中创建“相关信息”“相关主题”“相关笔记”“延伸阅读”“文件地图”“来源地图”等独立章节来罗列内部链接，也不要在文末追加 Wiki Link 清单。来源材料简要记在顶部元数据即可；除非用户要求来源清单，或复现/审计确实需要逐项追溯，不另建文件清单。实际使用且有复用价值的外部网页、文档、论文或仓库仍可放在 `## 外部参考`，但该节不用于收集内部链接。

文件名应包含可搜索的主题关键词，例如：

- `Transformer Attention机制.md`
- `RAG 检索质量评估.md`
- `LoRA 参数高效微调.md`
- `LLM API调用与错误排查.md`

不要覆盖已有笔记，不要擅自重组用户的文件夹。

### AI 笔记的根目录位置

AI 学习笔记、AI 资料和其图片资源不得放在 `10. SAP notes` 或任何 SAP 专属子目录下。它们必须放在 Obsidian 根目录下、遵循现有根目录编号约定的 AI 文件夹中。

当前库的根目录编号为 `00`、`10`，因此当前应使用：

```text
20. AI notes/
```

如果以后根目录编号发生变化，先查看现有根目录并沿用同一编号体系；不要把 AI 文件重新放回 SAP notes，也不要随意使用未编号的根目录。笔记和 `Assets` 文件夹都应位于该 AI 根目录下面。

## 10. Canvas and Index Synchronization

如果当前 Obsidian 库使用 Canvas 或索引笔记作为导航，创建、更新、合并或改名后要核对对应的 Canvas/索引：

- 根文档链接、文件名和 Wiki Link 是否存在；
- 章节标题、目录编号和章节锚点是否一致；
- Canvas JSON 是否合法，edge 是否指向现有节点；
- 新笔记是否放在正确的主题层级，视觉风格、颜色、位置和箭头方向是否延续既有约定。

若 Canvas 章节节点只是导航标签，默认只写标题，不擅自添加章节链接；遵循该 Canvas 已有规则。找不到对应 Canvas 时报告 `[待确认]`，不要因为发现空白 Canvas 就自动新建或重排整个导航。只有用户明确要求修正 Canvas 时才修改其布局；仅要求记笔记时，必要的根链接同步属于正常范围。

## 11. Keep the Obsidian Skill Copy in Sync

本 skill 的 Codex 源文件位于当前项目的 `.codex/skills/note-taking/note-taking-ai/SKILL.md`。每次修改本 skill 的实质性内容后，默认必须把相同修改同步到 Obsidian 副本：

```text
00 Agent skills/skills/note-taking/note-taking-ai/SKILL.md
```

同步规则：

- 先更新 Codex 源文件，再更新 Obsidian 副本；
- 同步完成后逐字核对两份 `SKILL.md`，确保内容一致；
- 如果副本目录不存在，应创建目录后再复制；
- 如果用户明确说明某次修改不需要同步，才可以只修改 Codex 源文件；
- `agents/openai.yaml` 属于 Codex UI 元数据，不需要复制到 Obsidian，除非用户另有要求。

## 12. Generation Workflow

1. 阅读全部资料、附件和当前讨论；
2. 提炼可复用知识，区分来源事实、用户观察和推断；
3. 判断 AI 领域、主要主题和笔记类型；
4. 搜索已有笔记、索引、Canvas、相关标题和关键词；
5. 决定合并到已有笔记还是创建新笔记；
6. 按用户风格写正文、目录、代码、公式、实验数据和提醒；
7. 处理图片、确有帮助的正文内链和外部参考；内部链接从简，不增加相关链接清单；
8. 检查事实边界、敏感信息、重复内容、链接和文件位置；
9. 保存后验证 Markdown/YAML、目录、锚点、图片路径和 Canvas/索引关系；
10. 用简短结果说明报告文件、领域、类型和已加入的内容。

## 13. Final Quality Check

完成前确认：

- 主题分类、模型/框架/版本没有凭空编造；
- 资料中的核心结论、用户的真实观察和个人推断已区分；
- 代码、命令、配置、公式和关键参数可搜索、可阅读；
- 实验结果带有足够的上下文，不夸大结论；
- 目录只在需要时添加，且与标题/锚点同步；
- 图片已复制并嵌入，或明确使用了占位符；
- 只保留少量确实能帮助理解的正文内链；没有必要时不加；没有独立的相关笔记/相关信息/文件地图链接清单；
- 外部来源与个人经验分开；
- 只有存在实际外部链接时才添加 `## 外部参考`，没有链接时省略该标题；
- 没有把密钥、隐私数据或临时路径写入笔记；
- 未覆盖或改写无关的既有内容；
- Canvas/索引存在时已核对，找不到时已标记 `[待确认]`。
- AI 笔记没有放在 `10. SAP notes` 下，而是放在根目录统一编号的 AI 文件夹中。
- 本 skill 有修改时，Codex 源文件与 Obsidian 副本已同步且内容一致。

## 14. Output After Note Creation

最终只需简洁确认，例如：

```text
已整理 AI 笔记：

文件：
RAG 检索质量评估.md

领域：
LLM / RAG / Evaluation

类型：
概念 + 实验

已添加：
- 核心概念与对比
- 实验配置和指标
- 代码块与图片
- 必要时在正文相关位置加入少量内链；没有必要时省略
```

不要在用户没有要求时完整重复整篇笔记。

## Final Principle

> 不要替用户写一篇漂亮但难以复用的 AI 教材；要把资料中的可验证知识、用户的实际理解、代码、实验和限制，整理成以后真正能用于复习和实践的个人笔记。

不确定时保留不确定性，不要用流畅的语言掩盖证据不足。
