# 家庭记账操作技能

本技能适用于本项目的记账、分类、报表、核对和基础开发。执行账本操作前，先定位账本项目目录，并阅读其根目录的 AGENTS.md、docs/MIGRATION_NOTES.md 和 docs/FULL_VERSION_BLUEPRINT.md。

## 账户名称与用途匹配

- 用户说出的账户、品牌、支付方式、类别和用途可能是中文、日文、英文、罗马字或常见简称；不要只做逐字匹配。按“品牌 + 卡/钱包/积分/支付等产品类型”与账本当前账户和类别列表进行语义归一，忽略大小写、全半角、空格和常见标点。只在唯一对应时采用，并始终用账本中的规范名称；多项都可能时再询问，不得创建不存在的账户。
- 账户别名示例应由用户当前账本的账户列表决定；将品牌与产品类型一起匹配，唯一对应时返回规范账户名，多候选时询问，不预设任何个人账户。
- 明确说“午饭/午餐/晚饭/晚餐 + 已花金额”时，分类为 `餐饮`，按外食/在外用餐理解；日语 `ランチ/昼食/夕食/晩ご飯` 和英语 `lunch/dinner` 同义。买菜、超市食材归 `食材`，不作为外食。若支付设置中有互补场景，餐饮消费匹配正向的“外食/餐饮”规则，不匹配“所有餐饮之外的消费”；“除餐饮之外”“不含外食”“非餐饮”等否定条件必须按排除解释，不能只因其中出现类别词就套用。

## 账务处理

1. 币种未说明时默认JPY；只有明确说人民币、CNY或人民币元时才使用CNY（单独说“元”仍按JPY）。确认发生日期、金额和类别。使用记账软件时，若消费唯一匹配到用户保存的支付场景规则，按该规则确定默认付款账户；除此之外不得猜账户。缺少付款账户时，可把明确确认的损耗记作备查支出。
2. 按发生日使用15日至次月14日账期。日期边界由 `billing_cycle` 函数计算。
3. 将JPY与CNY分开报告。不同币种之间只在用户提供两边金额或汇率时记转账。
4. 转账和信用卡还款只改变账户余额，不是消费。信用卡消费才记支出；还款不得再记一次支出。
5. 把总额度和手工录入的可用额度快照保留为有日期的原始记录。额度差不是已确认债务，不能据此填充卡片欠款。软件界面里的当前可用额度从最近快照起，自动计入交易日期晚于快照日、或快照当天在快照录入后记入的卡消费（扣减）、退款/收入（增加）和还款转账（增加）；结果限制在0至总额度，不覆盖原始快照。该数值基于账内流水，不代表发卡行实时查询；没有快照时不能自行推算。
6. 只有明确确认的结算或自动扣款才可记录。未结算账单不得标成已结算。
7. 先保留原始来源，再添加规范化记录。任何推断都要写明；无法验证的历史合计放在迁移说明，不拆成虚构流水。
8. 住房、工资及其他固定收支只依据当前用户明确提供的资料记录；不得沿用其他用户的金额或个人财务规则。
9. 支付顺序只能读取当前用户在当前账本或软件设置中保存的规则；不得硬编码账户名称、支付偏好或来自其他用户的账户顺序。积分、券、钱包、银行账户与信用卡的规则按项目配置校验。
10. 软件支付设置是多条按领域/用途匹配的默认规则，没有全局单选项；每条规则可选适用交易币种JPY、CNY或不限。币种是交易原币限制，不是账户币种；币种匹配的通用规则优先于不限币种的通用规则，且不触发普通消费换汇。若新配置含有`account_order`，其中的规范账户名称及顺序是程序分摊的唯一依据，覆盖用途文字里旧的箭头顺序；旧配置没有该字段时仍兼容解析文字顺序。每条顺序必须是同一币种，积分只能放在JPY顺序中；用户本次明确指定账户或拆分时优先。程序不能按完整顺序覆盖全额时，必须追问实际付款账户/拆分，不能写入部分消费。场景规则不用于收入、转账、还款或自动扣款。Codex聊天中未收到用户明确授权时，不套用软件里保存的场景规则。

## 现金盘点

- 余额管理表显示全部非信用卡资产账户，包括银行、钱包、券/预付、交通卡、实体现金和积分；信用卡额度/债务不作为现金。PTS独立显示、核对，不折算进JPY/CNY。
- 项目初始快照没有提供实体现金余额；不得从钱包、银行或其它余额猜现金期初数。已有账户余额须从账本期初数与交易计算，不要重置或重复导入快照。
- 桌面软件“现金管理”表平时余额格只读。点击“调整差额”后所有余额格一起解锁并预填账面值；将金额/点数改成实盘数后点击“确认调整并记账”，留空项目保持不变。
- 实体现金首次盘点只建立期初余额，不伪造收入。已建账账户之后的差额：实体现金记“现金盘盈/现金盘亏”，其它货币资产记“余额盘盈/余额盘亏”，积分记“积分盘盈/积分盘亏”；相等时不新增流水。批量调整须原子保存，避免只成功一部分。
- 盘点日期使用软件读取的日本本地日期；已有备查交易不得因余额管理而重分类或重复录入。

## 运行与核验

- 命令入口：`python -m bookkeeping.cli`。
- 任何结构性修改前先备份数据库；备份命令：`python -m bookkeeping.cli backup`。
- 修改后运行项目README里的测试和 `validate`，报告真实结果。
- 完整版后续功能及逐阶段验收条件见 [FULL_VERSION_BLUEPRINT.md](../../../docs/FULL_VERSION_BLUEPRINT.md)。

## 对话式使用

默认由用户在Codex聊天中自然语言报账，Codex负责读懂、必要时澄清、写入SQLite并回报结果。不要把命令行操作转交给用户，除非用户明确要求学习或自行运行CLI。

若用户希望在本地程序中直接对话，可运行 `python -m bookkeeping.cli chat`。CLI默认调用本机 Ollama OpenAI 兼容接口和模型 `qwen3.5:4b`；本机接口可不填Key，客户端占位值 `ollama` 也可用。CLI远程服务可用 `HOUSEHOLD_BOOKKEEPING_API_URL`、`HOUSEHOLD_BOOKKEEPING_MODEL` 和 `HOUSEHOLD_BOOKKEEPING_API_KEY` 配置，且必须使用HTTPS。Windows桌面GUI的“API 服务设置”可新增、切换、删除多个OpenAI兼容服务配置，每项保存名称、完整接口地址、模型名和Key；停顿约0.8秒后自动保存。Key在窗口中明文显示，在用户配置目录以DPAPI密文保存。切换服务或修改接口/模型后清空旧对话历史，避免发送给新服务。程序校验模型候选字段后才写入SQLite；账户等关键信息不全时先追问。CLI远程密钥只从隐藏输入或环境变量读取。不得将密钥明文写进源代码、账本或日志。自然语言内容会发送给所选API服务；不要发送密码或完整卡号。若使用 NVIDIA API Trial，条款限制提交财务信息，不能用它处理真实家庭流水。详细说明见 [NATURAL_LANGUAGE_API.md](../../../docs/NATURAL_LANGUAGE_API.md)。

Windows用户也可双击桌面的“家庭记账”快捷方式或项目根目录的 `启动自然语言记账.vbs` 使用桌面窗口。右上角“API 服务设置”可新增、配置和切换服务；本机 Ollama 可不填Key。接口地址、模型和Key在屏幕上显示，停顿约0.8秒后自动保存，Key以DPAPI密文写入用户配置目录。“支付方式与用途”保存多条不同领域的规则，支付账户通过已登记账户下拉选择（不含积分），并可在“扣款顺序”中添加、移除和调整普通账户或积分账户；每条顺序限制为同一币种。规则另设适用交易币种（JPY、CNY或不限）；币种会参与程序级匹配。所有规则都会发送给模型，不再设置全局默认单选按钮。等待 API 期间界面必须保持响应并显示持续加载状态，直到收到回答或请求错误；同一时刻不能提交第二笔请求。GUI与CLI共用同一自然语言会话和账本规则。
